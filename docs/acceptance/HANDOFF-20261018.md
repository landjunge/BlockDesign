## Bedienung und genaue Grenzen

MySpace → Codeauftrag: Änderungswunsch → **Stand vorbereiten** liest den tatsächlichen
gespeicherten Projekt-/Snapshot-/Elementstand und publiziert nur einen unveränderlichen
CAS-Descriptor. Nach dem Vorbereiten wird eine SHA256 angezeigt. Quellcommit bleibt
unbekannt. Die normale lokale Whiteboard-/Ollama-Boxbearbeitung ist davon getrennt.

Mit ausdrücklich eingerichtetem Backend-Profil: **An ThreadDesk übergeben** legt
einen begrenzten Arbeitsthread mit Notiz und drei vorhandenen Datei-Verweisen an
(Descriptor, Original-HTML, PNG). Der tatsächliche Issued-Beleg muss dieselben Dateien
und Hashes bestätigen. Es startet noch kein Agent. Erst **Diesen Codeauftrag starten**
reicht `handoff.start` an die vorhandene Bridge ein. Die bestehenden Rechte und das
vorhandene Codex-Profil bleiben maßgeblich. Kontextdaten erteilen keine Toolrechte.

Gespeicherten Lauf abfragen liest tatsächliche Task-/Run-/Returnbelege. Nach
Verbindungsabbruch wird die vor Versand gespeicherte Kennung nur gelesen, nie mit
einer neuen Kennung blind wiederholt. Eine Rückfrage setzt nach ausdrücklicher
Antwort ausschließlich die vorhandene beobachtete Sitzung fort. Keine Nachlaufqueue,
keine automatische Wiederverbindung mit Schreibwiederholung und kein Modell-Polling.

Rückgaben lesen nur die festen vereinbarten Dateinamen. Quelldaten und PNG werden
begrenzt gelesen/gehasht und im vorhandenen CAS gespeichert. Rückvorschau und
Zusammenfassung sind **ungeprüft**. Vor Übernahme einer Rückvorschau/Entscheidung
müssen aktueller Projekt-Head, Entwurfsrevision, Descriptor-/HTML-/PNG-Hashes,
Issued-Hash, Original-Task, Bridge-Task, Run, Thread, Handoff-Revision und Return passen.
Ein neuerer Entwurf, fremder Reply oder andere Bytes unter derselben Rückgabe werden
abgewiesen. Keine Rückgabe überschreibt den Entwurf. Ein Klick auf Übernehmen,
Verwerfen oder Nacharbeit dokumentiert mit Begründung genau diese Entscheidung in
ThreadDesk; er ist kein Funktionstest, keine Gesamtprojektabnahme und kein weiterer Start.

Grenzen: maximal64 Zuordnungen pro Projekt,128 gespeicherte Operationen pro Zuordnung,
2MiB je Zuordnungsdatei, bis30s je ausdrücklichem Host-Schritt und8s pro MCP-Call.
Vorhandene PNG-/HTML-Grenzen bleiben1MiB/4MP beziehungsweise256KiB. Ein Inboxabruf
berücksichtigt höchstens die ersten50 eigenen Rückgaben; fehlt die genaue Return-ID,
wird keine fremde oder nur ähnlich aussehende Lieferung übernommen. Das ist eine
bewusste begrenzte erste Anbindung, keine allgemeine unbegrenzte Inboxsuche.

Auch Sprache/Zoom/andere gespeicherte Editoränderungen können einen neuen Head
erzeugen: die alte Bindung bleibt dann historisch und ihre Entscheidung wird
gesperrt. Anfragen lesen den festen gespeicherten Stand, nicht heimlich den jüngsten
Entwurf. Es gibt keinen automatischen Rebase oder impliziten Folgeauftrag.
Der unveränderte ursprüngliche `bridge_task_id` bleibt in der GET-Zuordnung
erhalten und kann über die vorhandene Bridge-`task_get` unabhängig gelesen werden;
das ist bei einem inzwischen veralteten UI-Stand der konkrete Nachweisweg.

## Betreiber-Voraussetzungen – derzeit noch nicht aktiviert

Der reguläre `scripts/server.py` startet `DesignWorkflow(projects)` ohne Client oder
Profile. Der sichtbare Zustand lautet daher **Backend-Projektprofil/Bridge-Fachclient
fehlt**; Codeübergabe/Start sind gesperrt. Das ist kein pauschaler read-only-Anspruch
über KiraBridge. Die bereits separat eingerichtete Bridge kann weiterhin ihre eigenen
autorisierten Aufgaben bearbeiten. Dieser Worker änderte weder Konfiguration noch Dienst.

Ein vertrauenswürdiges lokales Embedding kann die bestehenden Objekte verbinden:

```python
# Operator-owned startup code only; never values from browser/request/model.
server.design_workflow = DesignWorkflow(
    server.projects,
    FixedBridgeClient(loaded_bridge_config, "existing_operator_principal"),
    {exact_saved_project_id: {
        "cwd": canonical_authorized_source_project,
        "source_file": "existing-source.html",
        "preview_file": "agreed-return.png",
    }},
)
```

Keine zweite Credentialdatei wird benötigt: der optionale installierte KiraBridge-
Client verwendet dessen vorhandene private lokale Konfiguration/Token-Lesegrenze.
Dieses Projekt installiert das SDK nicht automatisch. Vor Aktivierung erforderlich:

1. Passender überprüfter KiraBridge-M2-/MCP-Client und festes bestehendes Betreiberprofil
   mit `task.read`, den benutzten `threaddesk.*`/`handoff.*`-Capabilities sowie bereits
   genehmigtem Codex-Programm/CWD. Mit vorhandener `bridge_readiness` konkret prüfen;
   ein grün erreichbarer HTTP-/Health-Endpunkt genügt nicht.
2. ThreadDesk-Peer mit tatsächlichem `get_return`/Issued-/Run-Vertrag; eng autorisierter
   vorhandener CAS-Quellenroot. Ohne `verified` plus tatsächliche Dateihashes verweigert
   der Adapter den Schritt. Browser kann diese Freigabe nicht setzen.
3. Exakte Projekt-ID und kanonischer absoluter Quellprojektpfad ohne Symlink-Traversal;
   feste direkte Dateinamen, keine URLs/Unterpfade. Tatsächliche Originaldatei muss
   vor Übergabe/erstem Start dieselben Bytes wie die importierte HTML-Quelle haben.
4. Betreiber entscheidet bewusst über die eingerichtete Modell-/Codeausführung und
   ihre vorhandenen Datenschutz-/Budget-/Sandboxgrenzen. Die Anbindung erweitert sie
   nicht. Gleiche UID oder CWD ist keine OS-Isolation. Codeänderungen an fremden
   Projekten, beliebige Ergebnisdateien, bezahlte Provideraufrufe oder Runtimeumbau
   wurden hier weder eingerichtet noch geprüft.

Eine normale Installations-/Runtimeaktivierung dieses optionalen Embeddings ist
noch offen; es wurde keine Konfiguration oder Betreiberfreigabe erfunden. Die
separate tatsächlich bestandene KiraBridge-App-Bildabnahme ist kein zusätzlicher
Nachweis, dass eine aktive ChatGPT-Sitzung diesen BlockDesigner-Workflow benutzt hat.

## English

Source implementation and isolated acceptance are complete in the stated scope;
the normal user runtime remains unconfigured and cannot start this adapter.
Prepare reads an exact saved design; issue attaches immutable CAS files/hash in
existing ThreadDesk notes/files without execution. Explicit start, answer, status,
inbox and decision reuse existing Bridge/M2 tasks and owned session/run contracts.
Uncertain sends are read by their original durable task ID, never automatically
submitted again. A fixed backend operator profile supplies credentials and source
paths; browser data cannot grant rights or configure a peer. No second queue.

Returned source/PNG stays unverified. A newer design, foreign run, changed repeated
reply or conflicting decision is rejected. Delivery never mutates the design.
Accept/reject/rework records a reasoned operator decision; it is not a function
test, overall acceptance, automatic application or a new run. Source commits and
preview/source relationships stay unknown unless independently evidenced.

Eleven targeted tests include real isolated MCP/ThreadDesk and an explicitly
synthetic own CLI fixture, exact-session question/answer and response-loss cases.
The final pure countercase also covers two designs mapped to the same source CWD;
its guard is local to the existing store/operator profile, not OS-wide isolation.
Actual Chrome tested the product UI at1180×760: a harmless own HTML file changed
position/colour, was independently rendered from its actual new bytes, and produced
the exact delivered/API PNG hash. No model/provider or user runtime was used.
An additional small DE/EN layout check verified only the corrected button wrapping,
without rerunning the successful roundtrip. The linked reports preserve original
hashes and show zero page errors/external browser requests. No cross-platform,
real-model, installed-runtime or active-ChatGPT workflow acceptance is claimed.
